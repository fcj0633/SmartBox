# CR-006 企业箱体与运输任务数据及事务设计

> 状态：**候选 BL-003 数据设计草案**，日期：2026-11-23。对应 [CR-006](../../management/changes/CR-006-多角色物流箱与运输任务平台.md)、[V1.1 需求变更](../../requirements/SmartBox多角色物流箱管理平台需求变更说明.md)与[概要设计](../architecture/CR-006-多角色运输业务概要设计草案.md)。本文件提供可评审的设计和 SQL 示例，**没有创建 Flyway V13 或执行数据库迁移**。原 BL-002、V1～V12、MQTT v1 和固件均不变。

## 1. 依据现有数据库确定兼容边界

从现有 Flyway 迁移核实：\`users.id\` 为 BIGINT、\`boxes.box_id\` 为 ASCII binary 的 VARCHAR(48)，\`nodes\` 以节点与箱体组合外键约束；\`user_box_access\` 只有用户和箱体的访问关系，**不构成所有权证据**。遥测表 \`telemetry\` 保存 \`device_ts\`、\`ts_src\`、\`time_uncertainty_ms\`、\`received_at\` 和唯一的 \`(node_id,boot_id,property_seq)\`；事件表 \`events\` 同时保留源时间、接收时间与事件身份；现有 \`alarm_state\` 的 UNKNOWN 与 EVALUATED 不得合并成“正常”。

候选新业务继续使用 MySQL 8/InnoDB、utf8mb4/ASCII binary 约定和**毫秒 UTC 时间戳**。不重建原始遥测表、不更改原有 \`received_at\` 兼容查询接口；新任务查询需要另设可信发生时间和归属判断。

## 2. 领域实体与候选数据库表

| 表或关系（拟议名称） | 核心字段 | 约束、授权与注意事项 |
|---|---|---|
| \`enterprises\` | id、name、status、created_at | 企业为新的业务主体，不能直接用原 roles 替代 |
| \`enterprise_members\` | enterprise_id、user_id、member_status、can_assign、can_takeover | 组合主键，成员状态和独立动作资格；原 LOGISTICS_OPERATOR 不自动变企业管理员 |
| \`box_ownerships\` | box_id、owner_type、enterprise_id/owner_user_id、created_by、created_at | 每个箱体一个当前所有者，两个归属字段必须恰好有一个非空；V1 不开放在线转让，变更留审计 |
| \`box_assignments\` | id、box_id、enterprise_id、rider_id、state、assigned_at、revoked_at | 历史分配全保留；不可将同箱分配直接覆盖成新骑手 |
| \`box_active_assignment\` | box_id、assignment_id | box_id 主键：**一箱至多一条当前有效企业分配**，需事务维护并验证父子 box_id 一致 |
| \`transport_tasks\` | id、transport_no、box_id、rider_id、status、item_name、item_description、started_at、ended_at、version、责任快照 | 对外编号不可复用；READY 可未绑定物品，ACTIVE 前必填；同箱 ACTIVE 强约束 |
| \`transport_idempotency\` | actor_user_id、action、request_key、request_hash、task_id、response_status | 同一幂等键相同请求返回同一结果，内容不同拒绝；提交与业务事务原子 |
| \`transport_guest_grants\` | id、task_id、code_hash、grant_version、issued_at、revoked_at | 凭据值不可明文存储；到期与任务完成时间联动；撤销提升版本 |
| \`transport_guest_sessions\` | id、grant_id、session_hash、expires_at、revoked_at、issued_at | 会话绑定唯一任务/签发版本；被撤销的 grant 不得继续使用旧会话 |
| \`transport_access_audit\` | id、actor_id、task_id、action、outcome、occurred_at、details | 不写原始验证码、Cookie、客户端口令等秘密 |

V1 的“单份物品摘要”优先直接存于 \`transport_tasks\`，无需额外物品清单表。若未来变更多件商品或逐件签收，再独立建立物品实体及迁移。对“谁在任务开始时拥有箱体”，应在任务保留受保护的**责任/权属快照**，不能仅查询今天的分配关系推断历史授权。

## 3. MySQL 8 关键约束示例（仅供设计审查，非实际迁移）

与既有表类型保持一致，以下片段重点展示强不变量，不宣称覆盖了所有外键、审计、权限及迁移数据处理。

\`\`\`sql
-- 注意：仅是评审片段，不得直接应用到项目数据库。
CREATE TABLE transport_tasks (
  id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  transport_no VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  box_id VARCHAR(48) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  rider_id BIGINT NOT NULL,
  status VARCHAR(16) CHARACTER SET ascii COLLATE ascii_bin NOT NULL DEFAULT 'READY',
  item_name VARCHAR(50) NULL,
  item_description VARCHAR(200) NULL,
  started_at BIGINT NULL,
  ended_at BIGINT NULL,
  version BIGINT NOT NULL DEFAULT 0,
  created_at BIGINT NOT NULL,
  updated_at BIGINT NOT NULL,
  active_box_key VARCHAR(48) CHARACTER SET ascii COLLATE ascii_bin
    GENERATED ALWAYS AS (
      CASE WHEN status='ACTIVE' THEN box_id ELSE NULL END
    ) STORED,
  CONSTRAINT fk_task_box FOREIGN KEY (box_id) REFERENCES boxes(box_id),
  CONSTRAINT fk_task_rider FOREIGN KEY (rider_id) REFERENCES users(id),
  CONSTRAINT chk_task_status CHECK (status IN ('READY','ACTIVE','COMPLETED')),
  CONSTRAINT chk_task_clock CHECK (
    (status='READY' AND started_at IS NULL AND ended_at IS NULL)
    OR (status='ACTIVE' AND started_at IS NOT NULL AND ended_at IS NULL
        AND item_name IS NOT NULL)
    OR (status='COMPLETED' AND started_at IS NOT NULL
        AND ended_at IS NOT NULL AND ended_at >= started_at)
  ),
  UNIQUE KEY uk_task_public_no (transport_no),
  UNIQUE KEY uk_task_active_box (active_box_key),
  INDEX ix_task_box_created (box_id,created_at,id),
  INDEX ix_task_rider_status (rider_id,status,created_at,id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_bin;
\`\`\`

**为何使用生成列唯一索引？** MySQL 8 的 UNIQUE 允许多个 NULL。READY 与 COMPLETED 的 \`active_box_key\` 为 NULL，不限制历史数量；只有 ACTIVE 行生成 box_id，\`uk_task_active_box\` 会拒绝同箱第二个 ACTIVE。这样即使两笔事务同时执行“先查当前无运输”，也不能提交两个 ACTIVE。

**注意**：数据库强约束只能保证同箱的唯一 ACTIVE，不能代替业务层的资格、设备在线、物品校验、审计和幂等。未执行真实 MySQL 迁移与并发试验前，不宣称示例 DDL 已经通过生产环境验证。

企业当前分配建议使用 \`box_active_assignment\` 的 \`box_id\` 主键来防止同箱两名骑手；新增分配和撤回时同时维护 \`box_assignments\` 历史和当前指针，要求它们在**同一事务**更新。可用复合外键或事务校验保证指针的 assignment 与 box_id 对应，不允许跨箱引用。

## 4. 事务协议与并发时序

### 4.1 创建 READY

1. 服务端验证登录身份、个人所有权或有效骑手分配；不信任客户端传入的“拥有者”字段。
2. 以 \`(actor_id, action, request_key)\` 或等效强约束记录幂等请求，检查请求指纹是否相同。
3. 签发唯一 \`transport_no\`、记录操作者/责任快照和 READY；创建与幂等结果同事务提交。
4. READY 不锁箱；多个 READY 可以共存，开始时必须重验。

### 4.2 开始 ACTIVE

\`\`\`text
BEGIN
  SELECT boxes ... WHERE box_id=? FOR UPDATE;   -- 同箱串行化
  校验任务=READY、物品已绑定、当前权属/分配/动作资格
  校验必需节点在线；异常/未知/过期要求用户二次确认并审计
  UPDATE transport_tasks
     SET status='ACTIVE', started_at=:serverUtcMs, version=version+1
   WHERE id=:id AND status='READY' AND version=:old;
  -- UNIQUE(active_box_key) 防止出现同箱第二个 ACTIVE
  写入幂等结果与业务审计
COMMIT
\`\`\`

收到数据库唯一性冲突时，将结果映射为**箱体已被占用**，不应重试成另一笔自动成功。若 HTTP 回包丢失，用户查询操作结果；同一幂等键/指纹不重新执行状态变化。锁顺序和超时策略需要在实现前固定。

### 4.3 结束 COMPLETED

\`\`\`text
BEGIN
  锁定当前 box 行及目标 task
  校验状态=ACTIVE、当前结束资格（或经审计企业接管）
  UPDATE transport_tasks
     SET status='COMPLETED', ended_at=:serverUtcMs, version=version+1
   WHERE id=:id AND status='ACTIVE';
  保存审计和幂等结果
COMMIT
\`\`\`

同事务更新任务结束与活跃占用（生成列将变为 NULL）。重复结束不允许重写 \`ended_at\`。设备离线允许有资格者结束；**结束只表明业务记录已关闭，不表明传感器恢复、客户签收或全部事件已到达。**

### 4.4 分配/撤权

新建分配：锁 \`boxes\` 与当前分配指针，检查企业所有权/成员动作资格，新增历史并写当前指针，唯一主键保证单箱当前关系。普通撤回：有 ACTIVE 时拒绝。紧急撤权：审计、撤销关系、阻断骑手后续敏感请求，但 **不自动关闭 ACTIVE**；另由具接管资格企业人员结束。历史责任快照不更新为新骑手。

## 5. 任务时间、遥测与事件关联

- **时间数据规范**：与现有表保持毫秒 UTC。任务边界 \`[started_at,ended_at)\`；进行中任务上界为服务端查询时刻。
- **设备采样时间**：\`telemetry.device_ts\`、\`events.device_ts\` 只有在来源/质量足够可信时才可能用于任务归属；\`ts_src='SNTP'\` 不意味着精确到毫秒，应结合 \`time_uncertainty_ms\` 和时钟语义。
- **边界保守判定**：例如采样时间误差范围 \`[device_ts-u,device_ts+u]\` 必须完全落在同一任务范围，否则标记未知/边界模糊；不跨任务猜测。
- **接收时间不可替代发生时间**：T1 的 09:30 数据在 11:30 才收到时，不能因为当前箱体正在执行 T2 就强行关联 T2。
- **事件与派生告警**：告警状态 \`started_at/updated_at\` 不一定等于原始事件采集时间；关联时需要查证来源事件可信时间，跨任务持续告警只向当前用户披露授权时段内的结果。
- **历史缺口**：设备离线、丢包、存储溢出、时间未知时，返回缺口/质量标签，不生成虚假正常点；TASK-009 未完成前不能声称掉电事件可靠补全。
- **索引建议**：评审新增 \`telemetry(box_id,device_ts,id)\` 等读取优化；只通过新 Flyway 迁移增加，先用真实测试数据 EXPLAIN 验证，不改历史迁移。

**查询执行必须先鉴权，再按单任务时间边界及字段白名单裁剪。** 当前箱体监测接口仍按 CR-004 的接收时间语义运行，不能被新任务查询静默改写。

## 6. 访客凭据安全设计

V1 工作默认：10 位密码学随机字母数字验证码，配合不可猜的运输编号；进行中和结束后 7 天有效；访客只读会话 30 分钟；默认每任务/来源 15 分钟内失败 5 次限制，另有 IP 限流。全部默认参数需要上线前安全复评。

凭据生成后由有资格的运输方主动交付。服务端只存足够安全的验证摘要（对高熵随机验证码推荐使用服务端秘密参与的 HMAC 或等效抗离线穷举方法）；若有交付需求，必须提供明确的一次性展示或安全转交流程。不要把原文写入数据库、URL、WebSocket 地址或日志。

访客会话推荐不透明随机 Token，存储其散列及所绑定 \`grant_id\` 与版本；优先通过 HttpOnly、Secure、SameSite Cookie 承载，服务端验证已撤销/重新签发和当前访问范围。真实部署需要 CSRF、跨站来源、缓存与速率控制专项检查；不要直接给访客颁发旧的箱体级 JWT。

## 7. 设计复核与开发门槛

| 门槛 | 最小证明 |
|---|---|
| 兼容性 | 与 V1～V12 的主键、时间、索引和外键类型一致；可在隔离 MySQL 8 重复迁移 |
| 并发一致性 | 至少 20 个同箱开始请求最多一 ACTIVE，跨箱不互相锁住，回滚与死锁有受控响应 |
| 权属与分配 | 跨企业权限拒绝、双分配排他、撤权重校验、历史责任不被覆盖 |
| 访客安全 | 错误/过期/撤销/重签，旧 Session 和 WS 停读，日志无敏感令牌 |
| 任务历史 | T1/T2、迟到补传、UNSYNCED、时间不确定边界及跨任务告警不泄露 |
| 设备兼容 | 无 MQTT Topic、固件协议、已部署命令行为的意外变化 |

本文件是**数据模型和事务的审查基线输入**，不是部署脚本、生产 Migration 或已验证设计。正式写入 Flyway 前，需要同步批准后的 REQ/接口及实际 MySQL 集成测试计划。

## 9. 演示优先简化：首轮优先采用的表设计（2026-11-23）

**本节优先用于 DEMO 实施，前述完整模型保留作为未来扩展候选。** TASK-011 实际只需 `enterprises`（演示企业及一个受控管理员）、`box_ownerships`（企业/个人当前所有者）、`box_assignments`（当前有效使用者）。不需要同时建设 `enterprise_members`、`box_active_assignment` 与分配历史双表、独立通用审计服务。记录关键操作可复用原有 `audit_logs`，不保存账号或验证码原文。

TASK-012 再追加 `transport_tasks`，沿用本文件第 3 节的生成列 `active_box_key` 唯一约束；重复操作先以任务状态守卫和清晰冲突处理，不必新增通用幂等任务表。TASK-013 按需追加最小访客验证码验证材料，使用有独立签名范围的短期任务只读凭据；暂不构建完整 grant/session 双表及撤销推送机制。**不能**借旧 JWT 让访客获得整箱权限。

任务历史只允许可信设备时间位于任务边界内的样本；无可靠发生时间时宁可显示缺口，不以收到时间猜测。此 DEMO 不展示完整补传可靠性。完整切片、最低测试及延后范围见[演示优先实施方案](../../development/guides/CR-006-演示优先实施方案.md)。没有实际执行任何 Flyway 迁移或 SQL 性能/并发测试。
