# 演示优先实施方案（CR-006）

> 日期：2026-11-23。决策来源：用户明确要求 SmartBox 以**项目演示**为主要目标，降低详细测试、极端边界和生产级非功能要求的投入。本方案是 [CR-006](../changes/CR-006-多角色物流箱与运输任务平台.md) 候选 BL-003 的**分阶段实施范围**，与 [V1.1 需求说明](SmartBox多角色物流箱管理平台需求变更说明.md) 配套。**冲突时按本文件确定首轮 DEMO 切片，未纳入首轮的原有需求仍保留为后续候选，不得标记已实现或已验收。** 本文件不修改已生效的 BL-002、MQTT v1 或实际设备代码。

## 一、演示交付目标

以现有真实 ENV/POSE、EMQX Cloud、Spring Boot、MySQL 和 Vue 为基础，完成一条用户能亲眼看到的业务链路：

```text
企业管理员（演示账号）管理自己的箱体
  → 将箱体分配给骑手（或骑手选择自有箱体）
  → 骑手填写物品摘要、开始运输
  → 真实设备/模拟节点继续上报环境数据
  → 骑手结束运输，历史留存
  → 普通用户凭运输编号与验证码查看本次运输的状态、环境和异常摘要
```

首轮可采用**一个演示企业、一个骑手、一个普通用户、一个真实箱体**；为显示跨角色差异可增加第二个虚构企业和箱体作为测试样本。真实板数据与 Mock 物流/地图信息要标记来源。运行界面要可信，不能将纯前端演示数值说成后端实时数据。

## 二、时间投入的优先级

| 等级 | 首轮内容 | 决定 |
|---|---|---|
| **P0：核心演示** | 企业箱体列表、可用箱体分配/收回；骑手“我的箱体”与 READY→ACTIVE→COMPLETED；物品摘要；单任务状态、环境历史和访客验证；三个入口真正调后端 | 必须完成 |
| **P0：最小数据安全** | 服务端身份及箱体/任务范围核验；禁止跨企业/跨任务读取；数据库层限制单箱多 ACTIVE；凭据不明文存储或输出到日志/URL；访客仅能只读一项任务 | 必须保留，复杂程度可低 |
| **P1：够用的体验** | 空态、离线/过期标识、两种屏宽、简单失败提示、当前任务/历史切换、清楚标识 GPS MOCK | 能展示即可 |
| **延后** | 企业成员邀请/组织层级、权属转让、精细岗位动作矩阵、多人轮班、紧急接管 UI、完整操作审计平台、访客验证码重签与主动撤销、推送即时吊销、复杂导出、自动数据留存删除、长期稳定压测 | 首轮不开发；有明确需要再单列 |
| **保留但不扩展** | 现有 TLS、MQTT、后端登录/权限和设备采样代码；TASK-009 Flash 补传、TASK-010 原有交付 | 不因 DEMO 需求重写或提前宣称完成 |

## 三、TASK-011 的轻量技术路线（具体到当前代码）

已核对 [V1__identity_and_nodes.sql](../../backend/src/main/resources/db/migration/V1__identity_and_nodes.sql)：`users.id` 为 BIGINT，`boxes.box_id` 为 VARCHAR(48)，已有 `roles`、`user_box_access`。`BoxAccessService` 目前只按现有角色和 `user_box_access` 校验，**它不是企业/个人资产所有权服务**。新业务应只增量扩展，不把 `user_box_access` 直接当“所有权”。

首轮建议只新增以下 **4 张小表**（名称仅为设计建议，真实 SQL 在 TASK-011 实施时完成）：

| 表 | 必要字段 | 作用 |
|---|---|---|
| `enterprises` | `id,name,admin_user_id` | 演示企业及唯一管理账号；**不做成员邀请** |
| `box_ownerships` | `box_id,owner_type,enterprise_id,owner_user_id` | 当前拥有者，企业/个人二选一，`box_id` 唯一 |
| `box_assignments` | `box_id,rider_user_id,assigned_at` | 当前有效分配，`box_id` 主键；撤回删除当前关系，历史如有需要依赖现有审计 |
| `transport_* 后续表` | 不在 TASK-011 提前创建 | 留给 TASK-012/013，避免一次写完所有表 |

前 3 张即可支持 TASK-011，第四行只是说明后续表不抢先实现；因此本切片**实际新增三张表**。一个已有的 `LOGISTICS_OPERATOR` 账号可经受控初始化绑定为某个企业的 `admin_user_id`；这不是把所有同角色账号自动授权成企业管理员。企业、骑手、个人箱体样本由受控种子数据准备，不做自助注册/资产转让。

建议新建独立的 `AssetService` / `AssetMapper`（名称可调整），提供以下最少能力：

| 场景 | 候选接口 | 关键限制 |
|---|---|---|
| 企业资产 | `GET /api/v1/enterprise/boxes` | 只列当前账号管理的企业箱体 |
| 可分配骑手 | 使用受控演示账号清单或简化查询 | 不提供公开搜索所有真实用户 |
| 分配 | `POST /api/v1/enterprise/boxes/{boxId}/assign` | 只允许该企业管理员；同箱一条当前分配 |
| 收回 | `POST /api/v1/enterprise/boxes/{boxId}/unassign` | ACTIVE 运输期间拒绝；首轮没有紧急接管 |
| 我的箱体 | `GET /api/v1/rider/boxes` | 个人拥有 + 当前被分配的箱体 |

这些是**候选接口**，不直接修改现有的 `GET /api/v1/boxes` 或放宽原设备控制权限。后续运输页面应调用新的业务查询接口；不要为方便把 `user_box_access` 当作所有权或把普通用户赋予设备控制权限。迁移只追加 V13 以后的新版本，不修改已应用 V1～V12。

## 四、TASK-012 / 013 的最小衔接

**TASK-012：** 保留单表 `transport_tasks`（物品名称和简述作为字段）、状态 `READY/ACTIVE/COMPLETED`、服务端起止时间，使用生成列 `active_box_key` 唯一索引阻止同箱双 ACTIVE。普通重复请求返回已有任务/清晰冲突即可；首轮不必另建通用幂等工作流、复杂重试队列或紧急接管状态机。开始时权限和在线状态必须再检查，结束时只允许任务操作者（企业在进行中不能直接撤回分配）。

**TASK-013：** 普通用户使用服务端签发的单任务验证码（安全随机，存安全验证摘要）；验证成功获得**独立于旧箱体 JWT** 的短期只读资格，服务端每次按 `task_id` 过滤。演示阶段可采用独立签名短期 token 与最少的访问验证接口；首轮不做独立会话库、验证码重签发、撤销推送链路及访客 WebSocket（页面用 REST 重新查询即可）。若对公网开放，请额外完成基础失败限流与来源配置；没有这些不得宣称公网安全可用。

任务历史先复用已有 `telemetry` / `events`，以**可信设备时间 + 任务开始/结束边界**做最小查询。不能确定时间归属的样本不显示为本任务事实，允许展示“数据不足/可能缺失”；不实施全面补传回放、复杂告警时间重算或长周期追踪。访客查询不直接暴露整箱历史或 `node_latest` 的后续任务值。

## 五、最小测试集：优先验证真实链路，不追求数量

| 用例 | 最低验收 |
|---|---|
| 1. 数据库/初始化 | 新迁移在隔离 MySQL 启动，演示企业、箱体、骑手可初始化并查询 |
| 2. 箱体分配与权限 | 企业管理员能分配并收回，骑手能看被分配箱体；另一账号不能越权分配/查询 |
| 3. 运输闭环 | 一个箱体能经历选箱→物品→开始→结束→下一次任务；重复开始不能形成第二个 ACTIVE |
| 4. 访客查询隔离 | 正确编号＋验证码能看所属任务；错误验证码或更换 task_id 不能查看别人的任务 |
| 5. 三端联调 | 企业看到资产/运输，骑手操作任务，用户能查看这一任务的真实/标注模拟数据；模拟器可替代实板复验 |

推荐 2 个并发请求验证唯一约束即可；**不要求**原设计中的 20 并发压力测试、全异常矩阵、24 小时稳定运行、全量重签撤销/跨任务补传研究。运行过的用例必须报告成功/失败，未跑的不能标通过。

## 六、实现顺序与停止条件

1. **TASK-011**：受控初始化企业/个人箱体 → 最简分配/收回 API → “我的箱体”，完成 1 个成功及 1 个越权实测。
2. **TASK-012**：运输任务表与单箱唯一 ACTIVE → 物品绑定/开始/结束 → 简单真实 MySQL 测试。
3. **TASK-013**：任务时间范围只读查询 → 访客验证 → 三套正式界面接入 → 真实硬件或模拟器的一次完整演示。
4. 主流程稳定后才考虑 UI 细节、补充自动化与生产级可靠性。TASK-009 仍是原有固件可靠性任务，不必为演示三端重新设计。

**完成口径：** 能在实际运行的 Spring Boot + MySQL + Vue 上连续演示三端核心业务；数据库和权限没有明显错误；未实现的边界明确列为“未覆盖”，不把 DEMO 当成生产验收。本文是实施取舍决定，不是本轮已开发通过的结果。
