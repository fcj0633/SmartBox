## 1. 为什么改

现有三端运输产品把企业、骑手、访客都作为需要同时完成的入口，虽已形成 TASK-011～014 的代码和演示闭环，但企业端功能不足，地图只有示意背景，UI 原型中多处按钮尚无真实交互。用户现明确要求**本阶段只建设企业端**，以选定的物流地图控制台原型为功能与视觉中心，尽可能补齐其主要管理、监测、运输及告警能力。

这不是回滚旧实现，也不代表旧三端代码不正确；是**下一阶段开发优先级和产品使用主体发生改变**。

## 2. 新旧范围对照

| 维度 | 旧三端方向 | 企业端 V2 方向 |
|---|---|---|
| 主用户 | 企业、骑手、普通访客 | **单一企业管理员** |
| 运输写入 | 骑手创建/开始/结束 | **企业直接创建/开始/结束** |
| 资产与来源 | 一个实际箱体为主，地图基本示意 | **1 REAL＋建议 5 SIMULATED**，独立身份和场景 |
| 地图 | 无实物 GPS，静态 MOCK 背景 | **可交互 MOCK 点位、路线、动态推进、轨迹** |
| 企业页 | 资产/运输简版，原型结构初步还原 | **原型五主页面＋运输管理，八个详情 Tab** |
| 告警 | 设备事件/告警只读为主 | 设备异常事实＋**简化人工确认/处理** |
| 骑手、客户、访客 | 路线必需 | **暂停建设/隐藏新导航**，历史代码不急删 |
| 工程标准 | 新角色及访客安全链路 | 演示质量、源可信、事务/权限底线、少量代表检查 |

## 3. 必须保留与不能偷换的规则

- 现有有效技术基线及历史报告不修改、不删除；设备和模拟器需要独立身份，实体上报不被模拟覆盖。
- 设备数据 REAL/SIMULATED 与位置 MOCK 是两个不同来源。实体没有真实 GPS，**不能把地图上的坐标说成 GPS 实测**。
- 运输 ACTIVE 的数据库单箱唯一约束保留；企业操作需服务端确认本企业资产资格，不能通过虚构骑手绕过。
- 告警恢复来自设备/服务端事实，管理员“已处理”不得强制改变真实异常状态。
- 原有 REST/WS/设备命令的授权/错误语义不因新 UI 扩容而放宽；演示不等于安全豁免。
- 不能用 V2 新需求文档反向宣称新功能已实现；各开发阶段需补齐适用设计、任务、测试与证据。

## 4. 文档优先级与过渡安排

**当前阅读顺序**：V2 产品需求 → 现有代码/有效契约 → 为 V2 编写的新实施设计；旧 CR-006、三端需求和 TASK-011～014 保留为历史已实现资料及迁移兼容依据。BL-002 中仍有效的设备和控制要求继续作为适用底线，不把“现行产品方向调整”等同全部历史 REQ 编号立即废除。

本轮仅更新产品需求和文档导航，未改 Java、Vue、数据库、Broker、固件或测试；原有任务与测试证据状态不追改。

## 5. 推荐后续实施边界

1. 先解决企业直接操作运输所需的表与服务修改，再推进地图任务路线。
2. 模拟箱体采用可复现输入，统计/地图/详情/告警读取后端同一来源。
3. 以 UI 五个主页面及八 Tab 的可用行为为目标，按 V2 产品需求的 P0 演示流程验收。
4. 开发新任务/TC 时使用尚未占用的编号，重新梳理适用追踪；旧 TASK/REQ 不复用、不抹除历史事实。
