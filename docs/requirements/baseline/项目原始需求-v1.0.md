# 多功能物流柜 —— 项目文档

| 项目名称 | 基于 OpenHarmony 的多功能智能物流柜 |
|---|---|
| 硬件平台 | 多块 BearPi-HM_Nano（Hi3861）+ E53_IA1 + E53_SC2 |
| 系统形态 | 箱内多节点采集 → MQTT 上云 → 后端聚合 → 用户/物流/外卖端展示 |
| 文档版本 | v1.0 |

---

## 一、项目概述

### 1.1 背景

普通物流与外卖配送中，箱体是"黑盒"：寄件人和收件人不知道箱内温湿度是否失控、箱体是否被倒置或抛掷、柜门何时被谁打开、包裹此刻在哪。冷链断链、药品失温、餐品被私自打开等纠纷，往往只能靠事后口说，缺乏可追溯的证据链。

本项目用低成本 IoT 组件把"黑盒"变成"可观测箱体"：箱内多块开发板各自采集环境、姿态、定位，通过 MQTT 上云，后端统一聚合成一个"箱体视图"，按角色分发给用户、物流公司与外卖骑手。

### 1.2 项目目标

1. **可感知**：温度、湿度、光照、三轴姿态、定位（当前伪实现）连续采集。
2. **会判断**：环境超限、倒置/跌落、柜门开合、哨兵被入侵，均能自动识别并分级告警。
3. **可追溯**：所有事件落本地 Flash，断网不丢，恢复后按序补传。
4. **分角色**：物流场景双方共享全量信息；外卖场景用户看环境与定位、骑手看开关门记录与哨兵提醒。
5. **可演进**：GPS 以 HAL 抽象 + Mock 实现，后续换真实模块不改上层业务。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| box_id | 物理箱体编号，如 `BOX-0001`，多节点共用 |
| node_id | 节点编号，如 `BOX-0001-ENV`，MQTT clientId 与之对应 |
| ENV 节点 | 装 E53_IA1 的板，负责环境采集与补光/通风 |
| POSE 节点 | 装 E53_SC2 的板，负责姿态、门倾角证据、本地声光、GPS Mock |
| 门证据 | 单节点给出的"疑似开门/关门"事件，需云端融合成箱体级结论 |
| 哨兵模式 | 布防期间任何开门/倾斜/倒置立即本地+远程告警 |

## 二、需求分析

### 2.1 用户角色与场景

| 角色 | 关注点 | 可执行操作 |
|---|---|---|
| 寄件人/收件人（物流） | 全程环境、轨迹、开关门记录、倒置告警 | 查看、订阅告警 |
| 物流公司 | 多箱体看板、异常箱体排序、责任界定 | 查看、导出记录 |
| 下单用户（外卖） | 箱内环境、骑手位置、是否被打开 | 查看环境与定位 |
| 外卖骑手 | 开关门记录（自证）、哨兵布防 | 布防/撤防、查看记录 |

### 2.2 功能需求

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| FR-01 | 环境采集 | 温度、湿度、光照，周期 1 s | 必须 |
| FR-02 | 环境判定 | 按物品画像阈值判定，3 帧去抖 + 回差 | 必须 |
| FR-03 | 姿态检测 | 正常/倾斜/侧翻/倒置四级，跌落冲击检测 | 必须 |
| FR-04 | 门开合识别 | ENV 光照证据 + POSE 倾角证据，云端 ±2 s 融合 | 必须 |
| FR-05 | 哨兵模式 | 广播布防，开门/倾斜/倒置/越界即时告警 + 本地声光 | 必须 |
| FR-06 | 定位 | GPS 伪实现，支持 FIXED/ROUTE/WALK 三模式 | 必须 |
| FR-07 | 事件记录 | 环形缓冲 + Flash 持久化 + 掉电恢复 | 必须 |

> 上表为项目**核心功能**，共 7 项。断网补传、下行命令、箱体聚合、角色权限、告警分级等属于支撑性能力，在后续设计章节中体现，不再单列为功能需求条目。

### 2.3 非功能需求

| 类别 | 指标 |
|---|---|
| 实时性 | 事件端到端 ≤ 2 s；心跳 30 s；哨兵告警 ≤ 1 s 本地响应 |
| 可靠性 | 连续运行 24 h 无重启；断电 10 次数据不错乱；断网 30 min 自动恢复 |
| 数据完整性 | 单节点事件不丢（本地容量 64 条，覆盖最旧）；补传不重复 |
| 资源占用 | 单节点 RAM 峰值 < 60 KB（不含 TLS），Flash 增量 < 200 KB |
| 安全 | 生产环境 TLS；节点只能发布自己的上行主题 |
| 可维护性 | 一套代码两个产物（角色宏）；协议字段有版本号 |
| 可用性 | App 在节点离线时明确提示降级，不展示过期数据 |

### 2.4 约束

- Hi3861 资源有限，不跑文件系统，持久化用 KV。
- E53 接口每板一个，采用"一板一扩展板"的多节点形态。
- GPS 本期伪实现，但接口与真实模块一致。

## 三、系统方案

### 3.1 总体架构

```
   App（用户端 / 物流端 / 骑手端）
        │  HTTPS + WebSocket
   后端服务：设备接入 · 箱体聚合 · 门证据融合 · 告警 · 权限 · 记录查询
        │  MQTT（每节点一条独立连接）
 ┌──────┴───────┬──────────────┐
 ENV 节点       POSE 节点       GPS 节点（可选）
 IA1            SC2            Mock / 真实模块
 温湿度光照      三轴姿态        定位
 补光灯/电机     D1/D2/GPS
 └──────┬───────┴──────────────┘
        同一物理箱体 box_id
```

### 3.2 多节点拓扑

| 节点 | 硬件 | 能力（capability） |
|---|---|---|
| ENV | BearPi + E53_IA1 | 环境采集 0x01、补光 0x02、电机 0x04 |
| POSE | BearPi + E53_SC2 | 姿态 0x08、本地声光 0x10、定位 0x20、哨兵 0x40 |
| GPS（可选） | BearPi + GPS 模块 | 定位 0x20 |

### 3.3 数据流

```
传感器 → 采集层(SensorFrame) → 节点业务判定 → 事件(BoxEvent)
      → 本地环形缓冲/Flash → MQTT 上报
      → 后端：去重 → 时序入库 → 箱体聚合/门融合 → 告警
      → App：REST 拉取 + WebSocket 推送
```

### 3.4 技术选型

| 环节 | 选择 | 理由 | 备选 |
|---|---|---|---|
| 设备侧协议 | MQTT 3.1.1 | 轻量、长连接、天然支持下行、官方例程齐全 | HTTP（无下行、开销大）、TCP 自定义（需自处理粘包/重连） |
| Broker | EMQX / Mosquitto | 自建成本低、支持规则引擎与 ACL | 华为云 IoTDA（免运维，topic 固定） |
| 后端 | Python FastAPI 或 Node.js | 上手快，WebSocket 方便 | Spring Boot |
| 存储 | MySQL/SQLite + 可选 InfluxDB | 事件用关系库，时序数据用 TSDB | 全用 MySQL |
| 前端 | 小程序 / Vue | 地图与实时推送成熟 | — |

## 四、硬件设计

### 4.1 器件清单

| 器件 | 数量 | 说明 |
|---|---|---|
| BearPi-HM_Nano 主板 | 2（+1 可选） | 每板一节点 |
| E53_IA1 | 1 | SHT30 0x44、BH1750 0x23；补光灯 GPIO_14、电机 GPIO_8 |
| E53_SC2 | 1 | MPU6050 0x68；板载 D1/D2 指示灯 |
| 供电 | 2 路独立 | 建议统一 5V 母线或双电源，避免共用劣质 HUB |
| 箱体 | 1 | 分层固定 ENV 与 POSE，留散热与拆装空间 |

### 4.2 装配要点

- ENV 节点贴箱内壁中部，避免正对补光灯与出风口，否则温湿度与光照读数失真。
- POSE 节点贴箱盖或箱底，**与箱体固连**才有姿态意义；排线避开开合铰链。
- 补光灯开启时会造成光照自污染，ENV 节点判定"开门"需排除补光状态。
- 两板同时上电需分别供电，避免电压跌落导致重启。

### 4.3 引脚与接口

| 节点 | 接口 | 用途 |
|---|---|---|
| ENV | I2C | SHT30、BH1750 |
| ENV | GPIO_14 / GPIO_8 | 补光灯 / 电机 |
| POSE | I2C | MPU6050 |
| POSE | GPIO | D1 / D2 指示灯 |
| GPS（可选） | UART | NMEA 输出 |

## 五、软件设计

### 5.1 模块划分

| 模块 | 职责 |
|---|---|
| `box_role` | 角色宏、node_id、capability 位、按角色装配任务 |
| `box_sensor` | 按角色封装 IA1/SC2，统一 `SensorFrame`，加速度 /2048 → g |
| `box_logic` | 环境判定、姿态分级、单节点门证据、哨兵、告警分级 |
| `box_event` | 事件环形缓冲、Flash 持久化、补传队列 |
| `box_gps` | `gps_fix_t` + Mock（FIXED/ROUTE/WALK） |
| `box_net` | WiFi、MQTT、SNTP、命令分发与能力位过滤 |
| `box_cfg` | 物品画像、box_id/node_id、网络与服务器配置 |
| `box_main` | 任务、队列、互斥量、看门狗 |

### 5.2 关键逻辑

**环境判定**：阈值来自物品画像；连续 3 帧同向超限才升为事件；回差 1 ℃/3 %RH 防抖；开门瞬间热浪不触发冷链告警（冷却 30 s）。

**姿态判定**：合盖静置 3 s 得到基准重力向量；`tilt = arccos(a·g/|a||g|)`；<10° 正常、10~45° 倾斜、45~90° 侧翻、≥90° 倒置；||a|-1g| > 0.5g 判冲击。

**门开合（两级）**：
- 节点级：ENV 光照跃升 3 倍且 >50 lx 持续 1.5 s → `DOOR_EV_OPEN(LIGHT)`；POSE 倾角 >25° 持续 1.5 s → `DOOR_EV_OPEN(TILT)`。
- 箱体级（后端）：±2 s 窗口融合。双源 → 高置信 `DOOR_OPEN`；仅倾角 >60° → 中置信；仅倾角 25~60° → 只报 `TILT`；仅光照 → 报光照异常。

**哨兵**：云端广播布防到所有节点，全部回执才生效；3 s 布防缓冲期；Pose 节点本地声光、ENV 节点电机短振；被打开立即 CRITICAL。

**GPS 伪实现**：固定坐标 / 路径点插值 / 随机游走三模式，带 ±3~5 m 噪声、电子围栏、静止降频、`valid=0` 降级测试；真实模块仅替换 `gps_get_fix()`。

### 5.3 状态机

- 节点级：INIT → MONITORING ⇄ SENTRY，网络断开进入 OFFLINE（本地能力不降级）。
- 箱体级（后端）：正常 / 告警 / 已布防 / 降级（按 `online_mask` 组合）。

### 5.4 核心数据结构

```c
typedef struct {
    uint32_t ts;         /* UTC 秒；离线时为 uptime */
    uint32_t boot_id;    /* 上电标识，用于离线时间校正 */
    uint8_t  node_role;  /* 1 ENV 2 POSE 3 GPS */
    float    temp, humi, lux;
    float    acc[3], tilt_deg;
    uint8_t  pose, door_ev, moving, sentry;
    gps_fix_t fix;
} SensorFrame;

typedef struct {
    uint16_t seq;        /* 节点内自增 */
    uint32_t ts;
    uint8_t  node_role, ev_src, type, level;
    int16_t  v1, v2;
    gps_fix_t fix;
} BoxEvent;
```

## 六、通信与接口设计

### 6.1 上行链路

```
设备上电 → WiFi STA 连接 → DHCP → SNTP 校时 → MQTT Connect
        → 订阅 cmd → 周期心跳 + 事件即时上报 → 断线重连 + 补传
```

| 参数 | 取值 |
|---|---|
| 端口 | 1883（内网调试）/ 8883（TLS，生产） |
| clientId | `node_id`（全局唯一，否则互踢） |
| keepalive | 60 s |
| clean session | true |
| QoS | 属性 0/1，事件 1，命令 1 |
| 心跳周期 | 30 s（可下发调整） |

### 6.2 Topic 设计

| 方向 | Topic | 说明 |
|---|---|---|
| 上行属性 | `box/{box_id}/{node_id}/property` | 周期状态 |
| 上行事件 | `box/{box_id}/{node_id}/event` | 事件（含 seq） |
| 上行回执 | `box/{box_id}/{node_id}/ack` | 补传确认、命令结果 |
| 下行命令 | `box/{box_id}/{node_id}/cmd` | 带 target_caps 与 request_id |
| App 实时 | `wss://host/ws?token=` | 后端聚合后推送 |

### 6.3 报文规范

**属性上报**

```json
{
  "v": 1,
  "box_id": "BOX-0001",
  "node_id": "BOX-0001-ENV",
  "role": "ENV",
  "caps": 7,
  "seq": 2048,
  "ts": 1730000000,
  "ts_src": "SNTP",
  "boot_id": 17338,
  "profile": "cold_chain",
  "env": { "temp": 5.2, "humi": 78.4, "lux": 12.0, "state": "OK" }
}
```

**事件上报**

```json
{
  "v": 1, "box_id": "BOX-0001", "node_id": "BOX-0001-POSE",
  "seq": 1535, "ts": 1730000000,
  "events": [
    { "seq": 1535, "type": "DOOR_EV_OPEN", "src": "TILT", "level": 2,
      "v1": 3200, "v2": 2,
      "loc": { "lat": 30.51234, "lon": 114.41234, "valid": 1, "src": "MOCK" } }
  ]
}
```

**下行命令**

```json
{ "v": 1, "request_id": "req-8801", "box_id": "BOX-0001",
  "cmd": "sentry", "params": { "on": true, "duration_s": 7200 },
  "target_caps": 64, "ts": 1730000000 }
```

**命令回执**

```json
{ "v": 1, "request_id": "req-8801", "node_id": "BOX-0001-POSE",
  "result": "ok", "ts": 1730000001 }
```

`result` 取值：`ok` / `ignored`（能力位不匹配）/ `busy` / `error`。

## 七、安全设计

| 层面 | 措施 |
|---|---|
| 设备身份 | 每节点独立三元组（ProductKey/DeviceName/Secret），clientId = node_id |
| 传输 | 生产用 TLS 8883；实验环境 1883 仅限内网，文档中明确风险 |
| 鉴权 | MQTT username = node_id，password = HMAC-SHA256(secret, ts) 或平台动态密钥 |
| ACL | 节点只能 publish `box/{box_id}/{node_id}/#`，只能 subscribe 自己的 cmd |
| 应用侧 | JWT + 角色鉴权；定位仅对授权用户返回 |
| 数据 | 只存必要字段；日志不落明文密码；事件保留期可配置 |

## 十、创新点与难点

**创新点**

1. 多节点"一板一扩展板"的箱体级聚合，单节点故障不导致整体失联。
2. 门开合采用"节点级证据 + 云端时间窗融合 + 置信度"的两级判定，兼顾断网留痕与低误报。
3. 同一固件通过角色宏与能力位适配物流/外卖两种业务，不下发两套固件。
4. GPS 以 HAL 抽象 + 可编排 Mock，演示可复现且有真实替换路径。

**难点**

1. 多设备时间同步与事件排序。
2. 光照/倾角逐源误判的边界处理（整箱搬运 vs 掀盖）。
3. Hi3861 内存与 Flash 约束下的持久化与补传。
4. 多板供电与箱内装配的稳定性。

## 十一、风险与应对

| 风险 | 应对 |
|---|---|
| clientId/三元组重复导致互踢 | clientId 由 node_id 派生，专门做冲突反证测试 |
| 双节点时钟漂移 | SNTP + 偏差阈值；融合窗口 ±2 s；离线用 boot_id 校正 |
| 门证据误判 | 双源高置信、单源标注；25~60° 无光照只报倾斜 |
| 多板供电不稳 | 独立供电、统一 5V 母线、上位机监测重启次数 |
| 后端工作量被低估 | 先用 EMQX 规则引擎/Node-RED/Python 小服务跑通聚合，不写完整平台 |
| 演示现场网络差 | 手机热点备份；断网降级与补传本身作为演示亮点 |
| 伪 GPS 被质疑 | 强调 HAL 抽象与可替换性，现场切换三种模式演示 |
