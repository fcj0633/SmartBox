# MOD-04 事件管理与可靠性

基线：BL-002；版本：1.0；组织重构已授权，迁移验收见CR-002。实现及SmartBox板端结果未验证。

## 背景、目标与职责边界

提供事件身份、可靠保存、精确确认、去重、补传和恢复。

适用角色：各事件产生模块、ENV/POSE、后端与授权追溯者。

不决定环境异常或哨兵侵入的业务含义，也不替查询视图决定权限。

本模块是所属业务及子需求的权威需求来源；系统总纲负责整体协作，契约负责协议细节。功能重组不代表六个微服务，不改变固件分层和现有后端。

## 场景与总体流程

1. 业务模块提供稳定事件和原始时间质量，本地先可靠保存再发送。
2. 后端校验并将事件与必要派生工作可靠提交，之后确认精确事件集合。
3. 设备仅释放已确认记录；确认丢失可重发，重复和乱序按唯一键处理。
4. 断网恢复补传；溢出、存储失败和掉电损坏明确报告，派生工作可恢复而非静默丢失。

前置条件：受控身份、归属、权限及适用配置已准备；官方IA1/SC2例程据用户反馈可编译、烧录、运行，但SmartBox集成仍待验证。触发为周期输入、授权操作或恢复事件，正常结果与降级结果都应可解释。

## 典型场景与完整分支

| 场景 | 前置/触发 | 正常流程 | 分支及异常 | 结束与结果 |
|---|---|---|---|---|
| 正常事件 | 源模块确认业务现象 | 本地持久→传输→事务保存→精确确认 | 回滚不确认，PUBACK不清理 | 原始记录及派生工作可恢复 |
| 确认丢失与乱序 | 原始身份稳定，投递重排 | 一致重复幂等保存和重确认 | 同键异内容拒绝审计 | 不误删未到达事件 |
| 容量及掉电 | 存储队列、元数据和确认清理 | 容量内保存恢复；满后覆盖报告损失 | 损坏/失败明确，不能任意无损承诺 | 可解释数据完整性 |

| TC | [TC-006](../../testing/cases/TC-006-事件持久与补传.md) |

**目标与业务场景：** 形成不重复身份，使供保存/确认/去重使用。适用场景是上表中相关监测、控制或恢复过程；本条验收聚焦事件身份与唯一性。

**输入：** 节点身份、持久代次和事件序号。

**处理目标与正常流程：** 形成不重复身份。前置条件满足后处理有效输入，形成供保存/确认/去重使用；若输入质量或授权不满足，进入明确拒绝/降级分支。

**现行规则：**

- 事件身份 node_id+boot_id+event_seq；boot_id 持久化递增且不得在同节点复用；event_seq 使用 uint32，耗尽前切换持久化的新 boot_id。
- boot_id 持久化失败时停止生成声称唯一的新事件并上报存储故障；节点角色和 node_id 变更需维护操作。

**分支、异常与恢复：** 代次写入失败停止声称唯一的新事件；序号耗尽切换持久代次，不复用。

**输出及跨功能关系：** 供保存/确认/去重使用。状态细节见模块“交互与状态数据”。

**权限与质量：** 角色范围及NFR见模块统一约束；具体业务授权与数据质量要求按本条规则和上下游执行。

**验收标准：** node_id+boot_id+event_seq及uint32边界保持，变更节点身份属维护行为。 对照关联TC保存真实输入、结果与证据；软件/模拟通过不得替代板端验证。

**待决：** Q-03、Q-12；见[系统总纲第十章](../00-系统需求规格说明书.md)，不得在实现时自行选择答案。

**目标与业务场景：** 先可靠保存再交发送队列，使待确认事件记录。适用场景是上表中相关监测、控制或恢复过程；本条验收聚焦本地持久化及保存失败。

**验收标准：** 至少64条未确认目标、FIFO及落本地先于可靠上报保留。 对照关联TC保存真实输入、结果与证据；软件/模拟通过不得替代板端验证。
