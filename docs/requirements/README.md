# 需求目录与管理规则

当前组织基线：BL-002；生效验收见CR-002。系统总纲负责全局定义，六份模块需求是模块业务权威来源，契约是协议细节唯一来源。当前已有软件闭环及基础真实双板验证，但不代表全部需求已验收，具体实现与证据见[项目入口](../../README.md)及[当前进度](../management/当前进度.md)。

系统需求 → MOD模块需求 → 模块内部REQ子需求 → Design → TASK → TC。

## 编号、状态与变更

MOD采用两位模块号；子需求采用REQ-Mxx-nnn，xx与所属模块一致、nnn为模块内稳定序号。新增功能优先归入已有模块并使用未用序号；只有新业务领域才增MOD。编号不得因章节移动重排，废止编号保留变更记录且不复用。初始47项清单完整，未来变化同步索引和CR，不复制一套旧编号。

状态仍为草案、已确认、开发中、待验收、已验收、已取消；规范沿用不等于实现完成。待决部分明确标记，不借重组批准规则。

CR-002只保留一次性迁移审计。历史文件中的旧编号反映当时状态，不作为当前正式标识。版本由Git保存，不建旧需求副本目录。

每条子需求必须有固定锚点、设计、TASK与TC；改动同步矩阵与反向关联。全局NFR、任务、用例等既有编号保持稳定。

## 六模块如何协作

MOD-01描述监测现象，MOD-02在布防条件下解释防护行为，MOD-03负责节点接入/通用控制，MOD-04保证事件保存/确认/恢复，MOD-05形成箱体聚合及查询内容，MOD-06决定谁能看到或操作什么。它们是跨端业务边界，不是六个Java包、六个固件线程或六个微服务。

例如远程输出同时涉及授权、设备控制及箱体结果展示；事件从监测现象进入可靠保存，再形成用户允许的查询视图。一个TASK可以为多个MOD提供共同基础，同一个REQ也可被多个TASK依次实现，不能把“任务1不对应模块1”直接视为设计错误。

## 怎样从需求追踪到实现和验收

1. 在系统总纲理解场景，再从上方唯一REQ锚点阅读完整规则/依赖/验收。
2. 沿[需求追踪矩阵](../management/需求追踪矩阵.md)找到Design、TASK、TC和交付阶段；六模块/47项/NFR集合不因README调整而改变。
3. 通过[任务索引](../development/tasks/README.md)与[固件](../../firmware/README.md)、[后端](../../backend/README.md)、[前端](../../frontend/README.md)导读定位实际代码及当前调用链；设计可能包含尚未实现目标。
4. 通过[TC索引](../testing/cases/README.md)查标准，再查[报告](../testing/reports)及[证据约定](../testing/evidence/README.md)确认哪个版本实际测了什么。

真实采集不等于完整环境/姿态算法，后端event_ack不等于板端Flash可靠性，模拟器支持五类命令也不代表真实固件已支持。TASK-007的基础真实双板结果只覆盖相关切片，只有该REQ全部适用验收条件和必需测试通过后才能标已验收；本索引不改业务需求状态。

新增/调整业务先按原编号规则和CR流程记录，再同步设计、协议、任务及测试；不要在README里新增阈值或补定未决生命周期。原始输入、已批准规范和历史发布的职责分别保持。
