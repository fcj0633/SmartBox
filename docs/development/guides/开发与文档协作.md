# 开发与文档协作

## 从需求到交付

1. 从需求目录选择已确认 REQ，阅读验收和契约；新需求先按模板建立，变更已有规则写 CR。
2. 从追踪矩阵进入设计和 TASK。明确一个负责人、输入输出、异常和完成标准。
3. 按实际修改更新设计与契约；前后端按相同契约实现，不互相猜测字段。
4. 执行关联 TC，报告记录版本、步骤、预期、实际、证据及结论。
5. 更新 TASK、ITER、当前进度和需求追踪；必需 TC 完成才可验收需求。
6. 发布记录列出实现/软件验证/硬件验证边界，固定源码和产物版本。

需求新增使用所属模块的 REQ-Mxx-nnn 未使用序号；后续TASK、TC及CR使用各自未使用的后续序号。编号不得回收。文档内容修正不一定需要 CR，影响业务规则/验收/接口则需要。

## 提交前检查

运行 python tools/check_docs.py，然后 git diff --check。检查不执行服务、数据库或板端测试。业务实现后再跑相应测试命令，命令须由项目实际存在的配置定义。

小步提交，每项提交关联 TASK/REQ；不把密码、原始个人日志、依赖目录、SDK 或固件写入 Git。项目远程仓库为 https://github.com/fcj0633/SmartBox.git，默认 main 分支；推送前检查远程更新，不强制覆盖已有历史。

## 跨平台与 SDK

默认文本 UTF-8/LF；原始需求通过 .gitattributes 保持字节。固件只在仓库编辑，向 SDK 项目专属目录单向同步并先检查差异。同步不删除官方例程，不运行全 SDK 镜像覆盖。

依赖官方说明锁定版本，再生成 Maven/前端配置。P0 目录不能当作已有可运行工程。

## 单人开发约定

当前全部任务由用户独立开发、验证及验收；Codex执行已授权工作时另记实际执行者。按依赖顺序推进，复杂任务拆内部步骤，不设置成员间交接、多人签字或并行人员安排。已完成任务及历史记录保留当时事实；历史A/B代号对应的当前后续责任均由用户承担，不追改冻结证据。

固件骨架详细设计集中在[TASK-002](../tasks/TASK-002-双角色固件骨架.md)，软件构建结果以其实际报告为准。后端与数据库基础详细设计集中在[TASK-003](../tasks/TASK-003-后端与数据库骨架.md)，操作顺序见[初始化/启动指南](后端数据库初始化与启动.md)；TASK-003基础开发与真实MySQL/HTTP验收已完成，完整业务闭环仍需TASK-004～006。
